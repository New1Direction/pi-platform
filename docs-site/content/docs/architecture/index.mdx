# Architecture Overview

PI Platform is built around three core guarantees:

1. **Determinism** — identical inputs always produce identical ledger entries.
2. **Isolation** — every agent runs inside a Wasmer WASM sandbox with capability deny-by-default.
3. **Auditability** — every execution is content-addressed and can be replayed with integrity verification.

## Key components

| Component | File(s) | Role |
|-----------|---------|------|
| `PiOrchestrator` | `src/pi_micro_agents/orchestrator/` | Accepts compositions, fans out to router |
| `AgentRouter` | `src/pi_micro_agents/orchestrator/router.py` | Keyword → agent class dispatch |
| `StateLedger` | `src/pi_micro_agents/orchestrator/` | Append-only SQLite WAL, content-addressed |
| `pi-extension-governor` | WASM runtime | Capability-gated sandbox for every agent |
| Console API | `src/pi_console/` | FastAPI boundary, JWT auth, tenant scoping |
| Frontend | `pi-console-frontend/` | Next.js 15 dashboard |

<Callout type="info">
The Rust core (PyO3) accelerates the agent fabric by up to **12.5×** vs pure Python for per-agent runs. The batch path benchmarks at ~2.1× faster for full fan-out scenarios.
</Callout>

## Tenant isolation

Every write to the `StateLedger` is stamped with the authenticated `tenant_id` from the JWT. The Replay API enforces read scoping — a tenant can only fetch their own ledger entries. IDOR is blocked at the API boundary.

```
POST /compositions/submit
  X-Tenant-ID: org-a          ← must match JWT claim
  Authorization: Bearer <JWT> ← tenant_id extracted here

GET /replay/get?ledger_id=X
  X-Tenant-ID: org-a          ← ledger row must belong to org-a
```
