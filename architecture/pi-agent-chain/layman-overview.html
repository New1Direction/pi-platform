What is pi-semantic-recon?

A plain-English explanation of the deterministic API reverse-engineering runtime

🚨 The Problem: Reverse-Engineering APIs Is Full of Guesswork

When you try to figure out how an undocumented API works by watching its network traffic, most tools just guess:

  • • "This looks like a user ID" — but what if it's a session token?
  • • "This endpoint returns JSON" — but what if it only returns JSON sometimes?
  • • "These two requests are the same" — but what if the server response depends on your login state?

Guesswork leads to broken clients, security holes, and wasted time.

✅ The Solution: Prove Everything, Guess Nothing

This system refuses to guess. Every claim about the API must pass through 6 layers of verification before it becomes a "fact." If the system can't prove it, the claim stays marked "unverified" — forever.

What Goes In

  • • Raw HTTP traffic captures (pcap, proxy logs, browser dev tools)
  • • Request/response pairs with headers and bodies
  • • No documentation, no prior knowledge of the API

What Comes Out

  • • A typed OpenAPI 3.0 specification
  • • Every field typed (UUID, JWT, email, timestamp...)
  • • Every endpoint with methods and status codes
  • • Auth patterns documented (token rotation, CSRF coupling)
  • • A list of what the system couldn't verify

Why It's Different

  • • Most tools guess field types and blend conflicting observations
  • • This system refuses to guess — unverified claims stay CONTESTED
  • • Most tools collapse conflicts into a "best guess"
  • • This system preserves conflicts as explicit structures for human review

Analogy: Courtroom vs. Polling

Imagine two witnesses disagree on what color a car was. Most tools take a poll: "2 people said blue, 1 said red, so it's probably blue." This system says: "We have a conflict. Both testimonies are preserved. We need more evidence — maybe surveillance footage — before we declare a fact."
